After you [install and start]({{< ref "/amplify/nginx-amplify-agent/install/installing-amplify-agent" >}}) F5 NGINX Amplify Agent, it should start reporting right away, pushing aggregated data to the Amplify backend at regular 1 minute intervals. It'll take about a minute for a new system to appear in the Amplify web interface.

If you don't see the new system or NGINX instance in the web interface, or if some metrics aren't being collected, please review the following detailed troubleshooting steps:

  1. **Installation Verification**: Ensure the NGINX Amplify Agent package has been successfully [installed]({{< ref "/amplify/nginx-amplify-agent/install/installing-amplify-agent" >}}). Check the installation logs for any warnings or errors that might have occurred during the process. If issues are found, re-install the package and ensure all dependencies are met.
  2. **Process and Log Verification**: Confirm that the `amplify-agent` process is actively running. You can use commands like `ps aux | grep amplify-agent` to check its status. Additionally, verify that the agent is updating its [log file]({{< ref "/amplify/nginx-amplify-agent/install/configuring-amplify-agent#agent-logfile" >}}) regularly. If the log file is not updating, check for permission issues or errors in the log file itself.
  3. **User Consistency**: Ensure that the NGINX Amplify Agent is running under the same user as your NGINX worker processes. This can be verified by checking the user configuration in both the NGINX and Amplify Agent configuration files. Mismatched users can lead to permission issues and failed metric collection.
  4. **Absolute Path Requirement**: Start the NGINX instance using an absolute path. The NGINX Amplify Agent **cannot** detect instances launched with a relative path (e.g., "./nginx"). Use the full path to the NGINX binary in your startup scripts to avoid detection issues.
  5. **Process Visibility**: Ensure the [user ID used by NGINX Amplify Agent and the NGINX instance]({{< ref "/amplify/nginx-amplify-agent/install/configuring-amplify-agent#overriding-the-effective-user-id" >}}) has permission to run `ps(1)` to view all system processes. If `ps(1)` is restricted, the agent may not detect the NGINX master process. Adjust permissions or run the agent as a user with sufficient privileges. If `ps(1)` is restricted for non-privileged users, NGINX Amplify Agent won't be able to find and properly detect the NGINX master process.
  6. **Time Synchronization**: Verify that the system time is correctly synchronized with a reliable time source. Use tools like `ntpdate` or `chrony` to ensure the system clock is accurate. Incorrect time settings can prevent graph data from displaying correctly.
  7. **Stub Status Configuration**: Ensure `stub_status` is [configured correctly]({{< ref "/amplify/nginx-amplify-agent/configuring-metric-collection" >}}) and that the `stub_status module` is included in the NGINX build. Confirm this by running `nginx -V` and checking for the `--with-http_stub_status_module` flag. Misconfiguration can lead to incomplete metric collection.
  8. **Log File Accessibility**: Ensure that NGINX [access.log](http://nginx.org/en/docs/http/ngx_http_log_module.html) and [error.log](http://nginx.org/en/docs/ngx_core_module.html#error_log) files are readable by the user `nginx` or the [user](http://nginx.org/en/docs/ngx_core_module.html#user) specified in the NGINX configuration. Check file permissions and ownership to prevent access issues.
  9. **Configuration File Permissions**: Verify that all NGINX configuration files are readable by the NGINX Amplify Agent user ID. Check the owner, group, and permissions of these files to ensure the agent can access them without restrictions.
  10. **Additional Configuration Steps**: Perform any extra [configuration steps required]({{< ref "/amplify/metrics-metadata/nginx-metrics#additional-nginx-metrics" >}}) for collecting additional metrics. This may include enabling specific modules or adjusting configuration settings to capture the desired data.
  11. **DNS Configuration**: Ensure the system DNS resolver is correctly configured and that *receiver.amplify.nginx.com* can be successfully resolved. Use tools like `nslookup` or `dig` to test DNS resolution. Incorrect DNS settings can prevent the agent from communicating with the Amplify backend.
  12. **TLS/SSL Connectivity**: Confirm that outbound TLS/SSL connections from the system to *receiver.amplify.nginx.com* are not restricted. Use `curl -v https://receiver.amplify.nginx.com` to test connectivity. If restrictions exist, consider [configuring a proxy server]({{< ref "/amplify/nginx-amplify-agent/install/configuring-amplify-agent#setting-up-a-proxy" >}}) for the NGINX Amplify Agent.
  13. **Security Module Interference**: Check that *selinux(8)*, *apparmor(7)*, or [grsecurity](https://grsecurity.net) are not interfering with metric collection. For *selinux*, review **/etc/selinux/config** and try `setenforce 0` temporarily to see if it resolves the issue. Adjust security policies as needed to allow metric collection. E.g., for _selinux_(8)* review **/etc/selinux/config**. Try `setenforce 0` temporarily and see if it improves the situation for certain metrics.
  14. **Kernel Restrictions**: Be aware that some VPS providers use hardened Linux kernels that may restrict non-root users from accessing */proc* and */sys*. This can affect metrics related to system and NGINX disk I/O. Consider running the NGINX Amplify Agent as `root` or adjusting permissions for */proc* and */sys/block* to allow access. Metrics describing system and NGINX disk I/O are usually affected. There is no easy workaround except for allowing NGINX Amplify Agent to run as `root`. Sometimes fixing permissions for */proc* and */sys/block* may work.
